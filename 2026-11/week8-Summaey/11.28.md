## 📚 Maven 仓库

**仓库的作用**：Maven 的仓库用来 **存储和管理 jar 包**。

### 三类仓库与查找顺序

| 查找顺序 | 仓库类型 | 说明 |
|:---:|:---|:---|
| ① | 本地仓库 | 本机 `.m2` 目录，速度最快 |
| ② | 远程仓库（私服） | 公司 / 团队内部共享 |
| ③ | 中央仓库 | Maven 官方公共仓库 |

> [!NOTE]
> 依赖查找顺序：**本地仓库 → 远程仓库（私服）→ 中央仓库**。找到即停止，不会继续向下查找。

## 📦 Maven 坐标（GAV）

Maven 中的坐标是 **资源（jar）的唯一标识**，通过该坐标可以 **唯一定位资源位置**。
使用坐标可以 **定义项目**，也可以 **引入项目中需要的依赖**。

### 坐标组成（G-A-V）

| 坐标字段 | 含义 | 示例 |
|:---:|:---|:---|
| `groupId` | 组织名称（通常为域名反写） | `com.example` |
| `artifactId` | 模块名称 | `my-app` |
| `version` | 版本号 | `1.0.0` |

### 版本分类

| 版本类型 | 含义 | 适用场景 |
|:---:|:---|:---|
| `SNAPSHOT` | 功能不稳定、尚处于开发中的快照版本 | 开发阶段 |
| `RELEASE` | 功能趋于稳定、停止更新，可用于发行的正式版本 | 上线发行 |

> [!WARNING]
> 开发阶段使用 `SNAPSHOT`，正式发布使用 `RELEASE`，不要把快照版本直接发到生产环境。

## 🔗 Maven 依赖配置

### 基本依赖配置

在 `pom.xml` 中通过 `<dependencies>` 声明依赖，每个依赖用 `<dependency>` 定位：

```xml
<dependencies>
    <dependency>
        <groupId>com.example</groupId>
        <artifactId>my-module</artifactId>
        <version>1.0.0</version>
    </dependency>
</dependencies>
```

### 如何排除依赖

当依赖间接传递了不需要的 jar（如版本冲突）时，使用 `<exclusions>` 排除：

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>my-module</artifactId>
    <version>1.0.0</version>
    <exclusions>
        <exclusion>
            <groupId>org.unwanted</groupId>
            <artifactId>unwanted-jar</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

> [!WARNING]
> - 依赖配置一旦变更，记得 **重新加载** Maven 项目；
> - 引入的依赖本地仓库不存在时，记得 **联网** 下载。

## 🔄 Maven 生命周期

Maven 拥有三大生命周期：`Clean`、`Default`、`Site`，每个生命周期由多个 **阶段（phase）** 组成。

### 常用阶段

| 阶段 | 命令 | 作用 |
|:---:|:---|:---|
| clean | `mvn clean` | 清理（删除 `target` 目录） |
| compile | `mvn compile` | 编译源码 |
| test | `mvn test` | 运行测试 |
| package | `mvn package` | 打包（jar / war） |
| install | `mvn install` | 安装到本地仓库 |
| deploy | `mvn deploy` | 部署到远程仓库（私服） |

> [!NOTE]
> `deploy` 将最终的包复制到 **远程仓库（私服）**，以与其他开发者和项目共享。

## ✅ JUnit 单元测试

### 作用

测试类中方法的 **正确性**。

### 优点

| 优点 | 说明 |
|:---|:---|
| 代码分离 | 测试代码与应用代码分开，便于维护 |
| 自动报告 | 可自动生成测试报告（通过：绿色，失败：红色） |
| 相互独立 | 一个测试方法失败，不会影响其它测试方法 |

### 命名规范

| 对象 | 要求 | 示例 |
|:---:|:---|:---|
| 类名 | `XxxxTest`（**规范**） | `UserServiceTest` |
| 方法名 | `public void xxxx(){...}`（**规定**） | `public void testLogin(){...}` |

## 🧪 断言（Assertions）

### 为什么使用断言？

单元测试方法运行 **不报错，不代表业务方法没问题**。
通过断言可以检测方法运行结果是否与预期一致，从而判断业务方法的正确性。

```java
import org.junit.jupiter.api.Assertions;

Assertions.assertEquals(预期值, 实际值);
Assertions.assertTrue(条件);
Assertions.assertNotNull(对象);
```

> [!TIP]
> 断言是单元测试的 **灵魂**：没有断言的测试方法只是"把代码跑了一遍"，并不能证明业务逻辑正确。

## 🏷️ 常用注解

### 参数化测试

JUnit 单元测试方法 **可以** 声明形参，实现参数化测试，配合 `@ParameterizedTest` 与 `@ValueSource` 使用：

```java
@ParameterizedTest
@ValueSource(ints = {1, 2, 3})
void testIsPositive(int num) {
    Assertions.assertTrue(num > 0);
}
```

### 初始化与资源释放

| 注解 | 作用 | 执行时机 |
|:---:|:---|:---|
| `@BeforeEach` | 每个测试方法运行前做初始化 | 每个方法前 |
| `@BeforeAll` | 所有测试方法运行前初始化一次 | 整个类前 |
| `@AfterEach` | 每个测试方法运行后释放资源 | 每个方法后 |
| `@AfterAll` | 所有测试方法运行后释放资源一次 | 整个类后 |

> [!NOTE]
> `@BeforeAll` / `@AfterAll` 默认需要声明为 `static` 方法（否则需修改 `@TestInstance` 生命周期）。

## 🎯 Maven 依赖范围（Scope）

### 如何指定依赖范围

在 `<dependency>` 中通过 `<scope>` 指定：

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.0</version>
    <scope>test</scope>
</dependency>
```

### 常见取值对比

| scope | 编译 | 测试 | 运行 / 打包 | 典型场景 |
|:---:|:---:|:---:|:---:|:---|
| `compile`（默认） | ✅ | ✅ | ✅ | 大多数业务依赖 |
| `test` | ❌ | ✅ | ❌ | JUnit、Mockito |
| `provided` | ✅ | ✅ | ❌ | Servlet API、Lombok |
| `runtime` | ❌ | ✅ | ✅ | JDBC 驱动 |

> [!WARNING]
> **`test` 与 `provided` 的区别**（高频易错点）：
> - `test`：只在 **测试阶段** 生效——编译测试代码、运行测试时可用，主代码编译时不可用；
> - `provided`：**编译和测试** 阶段都可用，但 **运行时 / 打包时不打入**，由运行环境（如 Tomcat、JDK）提供。
>
> 一句话记忆：`test` 是 **"只给测试用"**，`provided` 是 **"环境已提供，别打包进来"**。

<details>
<summary>点击展开详情：Scope 详细解释</summary>

#### `compile`（默认）

- 编译 ✅、测试 ✅、运行 / 打包 ✅
- 不写 `<scope>` 时默认生效，依赖会传递给下游项目。
- 适用：绝大多数业务依赖，如 Spring、MyBatis。

#### `test`

- 编译 ❌、测试 ✅、运行 / 打包 ❌
- 只在测试代码编译与运行阶段参与，不会被打进最终产物。
- 适用：JUnit、Mockito 等测试专用依赖。

#### `provided`

- 编译 ✅、测试 ✅、运行 / 打包 ❌
- 编译和测试阶段可用，但打包时 **不包含**，期望由运行环境提供。
- 适用：Servlet API（由 Tomcat 提供）、Lombok（编译期生效）。

#### `runtime`

- 编译 ❌、测试 ✅、运行 / 打包 ✅
- 编译时不需要，但运行时必须存在。
- 适用：数据库驱动（JDBC），运行时通过反射 / SPI 加载。

</details>
